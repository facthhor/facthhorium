# v0.4 preview verification

The preview is v0.3.0 with the Q8 global-KV program (`program/llm.loom`, `program/storage.loom`) and a 204,800-token context cap in `facthhorium.json`. The other program files, the relay and the Pi extension are byte-identical to v0.3.0.

## Q8 layout

The eight global attention layers store K and V as int8 codes with one FP16 scale per 32 channels. A page holds 16 positions of one layer: K codes (16,384 bytes), K scales (1,024), V codes (16,384) and V scales (1,024), 34,816 bytes in all, or 2,176 bytes per position per layer against 4,096 for FP16. The kernels keep their FP16 logical addresses and `global_kv_address` maps them onto the compact pages. The sliding-window rings and the drafter cache stay FP16.

## The depth-3 bug and its fix

Earlier Q8 builds drifted from FP16 at draft depth 3 and garbled long verbatim copies (92 of 120 lines on the copy test). Depth 0 was exact. The drift depended on request history and on the memory budget, and it fell into a few discrete output classes across engine sessions.

Cause:

1. When a request ends, the runtime releases the backing of the KV blocks it no longer needs. A later request gets those blocks back with fresh backing from a shared pool, which is not cleared. Slots the new request has not written yet hold whatever bytes the pages carried before.
2. A Q8 page is 34,816 bytes (2^11 × 17), so it does not line up with the power-of-two backing pages. Reused pages shift old code bytes into scale slots, where they decode as Inf, NaN or huge FP16 scales. FP16 pages (32,768 bytes) stay aligned, so their stale content is ordinary finite KV.
3. The multi-token span readers used by speculative verification load whole 16-position pages. Positions after the last query get attention weight 0, but the value still enters `o = fma(v, p, o)`, and 0 × Inf is NaN.
4. The attention combine quantizes its output for the next projection. Its maximum ignores NaN, and the integer conversion turns NaN into 0, so those dimensions were silently zeroed. The result was a small perturbation that flipped close token choices rather than visible garbage.

The fix: in `g_ink_attn_split_span_q1`, `_q2` and `_q4`, the near-page value load uses a variant (`global_kv_load_8x2x8x16x8_m`) that sets the scale to zero for positions after the span's last query. Those positions already have weight 0 for every query, so the change is exact for valid data. It costs one select per value load.

How it was isolated, all on fresh engines with greedy decoding at depth 3:

| Test | Result |
|---|---|
| `chat/25 → div7not11 → primes100`, plain Q8 | diverges at token 321, the first page `div7not11` never wrote |
| same without `chat/25` first | identical to the FP16 reference |
| rewrite the masked tail with its own bytes before the readers | still diverges at 321: the bytes matter, not when they were written |
| zero only the masked K / only the codes / only part of the tail | still diverges |
| zero only the masked V, or only the scales | identical |
| span readers with the V-scale mask (this preview) | three repro sequences, 10 of 10 requests identical |

## Agreement

The reference is an FP16-layout build that rounds every stored K and V value to the same Q8 grid, so differences come from the Q8 code paths and not from rounding. 45 short prompts (26 chat, 14 math, 5 code), greedy, 512 tokens, maximum effort, depth 3:

| Build | Identical to the reference |
|---|---|
| plain Q8 (before the fix), same session | 30/45 |
| Q8 with the V-scale mask | 44/45 (one math prompt diverges at a near-tie after 317 tokens; teacher-forced top-1 99.995%) |
| reference with the same mask | 45/45 (the reference itself is unaffected) |

The single divergence is not a remaining stale-memory read. Two further builds that are equally immune (the mask on K as well, or an extra kernel that zeroes the unwritten slots in memory) also give 44/45. The divergence stays on the same prompt when only the readers change, and moves to another math prompt (a near-tie after 416 tokens) when the extra kernel adds launches.

## Verbatim copy

Rust source the model cannot have memorized, one quoted line per request, the six lines after it, greedy, depth 3, `--max-tokens 1500`. Ten probes at 50,084 input tokens and ten at 95,746 returned 120 of 120 lines exactly (plain Q8: 92 of 120; FP16 v0.3.0: 120 of 120).

## Quality gate

Temperature 1, top-k 0, top-p 1, maximum effort, draft depth 3, 204,800-token context. The gate used the release program files. The agreement and copy runs used the same `llm.loom` and `storage.loom` with the tool parser from before the trailing-JSON fix, which only affects tool calls. All of them ran with the prompt cache disabled (session and prefix capacity 0). Earlier tests showed that caching does not change outputs (45/45 identical with and without, for both the Q8 and FP16 layouts). With the release card itself (prompt cache on), a 204,007-token request, the longest the cap allows with a short reply, completed with GTT at 24.7 GiB and 2.7 GiB of system memory available.

- 14/14 math problems with exact answers.
- 5/5 code problems checked by unit tests.
- 4/4 vision checks, including a 16-image request.
- 1/1 tool call.
